# M4-G11 brief: Validation records and diagnostics

Read with `M4-common.md`. Stub: `papers/2026-10-17-geometry-lifecycle-map.md` §4.1 G11. Bead: `brepgpu-12s.12`.

**Purpose.** Define the native record model for findings: the measure before
and after healing; ISO 10303-59 layers; PDQ codes; threshold provenance; method
and accuracy; extreme location; action. Also the status set, including
indeterminate, and the roll-up from face to part to run.

**Decision it blocks.** M5 §4.6 and §5.5 records.

**Operator decisions that bind this lane.** D-partial-output (mesh the rest,
marked incomplete); D-profile (a named BRepGPU profile seeded from JAMA and
CAx-IF; users may tighten; loosening is recorded); D-PMI (warn and comply); the
internal-data rule (no JSON internally; JSON only at a presentation boundary).

**Questions.**
1. The status lattice: valid, valid with the goal unmet, indeterminate and
   refused, how they combine, and how mature checkers separate "could not
   evaluate" from "invalid".
2. The record schema, in native terms: fields, types and identity.
3. The BRepGPU profile: its starting thresholds with provenance (JAMA V5.1,
   CAx-IF, SASIG PDQ where readable) and the loosening record.
4. The human view: how a person reads a run's diagnostics (Parasolid fault
   model, SMESH compute errors, usd-brep requirement ids), derived from the
   same records.

**Measurement.** None.

**Output slug.** `validation-records`: `papers/2026-10-17-validation-records.md` and its sources TSV.

**Done when.** The record schema, the status lattice and roll-up rule, and the
human view. Every question has an evidence-backed answer or an explicit "the
literature does not say" with the measurement that would settle it.

**Return.** The lattice, the schema outline and the profile. Then the common
return items.
