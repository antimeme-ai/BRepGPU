# Iterative acceleration: actual integration seams and topology ownership

Source study, 2026-10-13. No product code, runtime installation or dependency adoption occurred. The conclusions below come from pinned source inspection; neither a C++ adapter nor GPU consumer has been executed in this study.

**The first useful integration is an owned batched geometry consumer beside SMLib. Its shipped Boolean APIs do not provide an evaluator replacement hook.** The public C++ geometry API can supply control data and split low-degree carriers into candidate patches. Python can query carriers and domains, or export them through USD, but does not directly expose degree/control/weight/knot access. This distinction determines what the first prototype can actually deliver.

## What unmodified SMLib exposes

### Python: carrier queries, not control-net extraction

`source/SmPyLib/stubs/usd_brep/__init__.pyi:240–313` and `source/SmPyLib/src/SmPyTypes.cpp:717–728,1208–1268` expose:

- `Face.surface()`, `Face.uv_domain()`, ordered oriented `Face.boundary_loops()`, `Face.classify_uv()` and face-aware closest point.
- `Surface.u_domain()`, `v_domain()`, `uv_domain()`, `evaluate()`, `derivatives()`, `normal()` and periodicity queries.
- `Edge.curve()`, parameter interval, endpoint/incident-face queries and evaluation.

They do **not** bind `SmBSplineSurface.GetDegree`, control points, weights, knot vectors, `SplitAt`, `CopyAnalyticAsNurb`, or edgeuse UV-curve access. `BSplineCurve` is an empty subclass binding; there is no bound `BSplineSurface` subclass. This is a source conclusion about this revision, not a claim about future APIs. [Bindings](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SmPyLib/src/SmPyTypes.cpp), [type stubs](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SmPyLib/stubs/usd_brep/__init__.pyi).

`Face.uv_domain()` is the rectangular box bounding the outer loop. It does not remove interior holes and does not mean every UV inside is on the trimmed face. `Surface.uv_domain()` can be wider still. `boundary_loops()` retains edge occurrence orientation, unlike a unique edge list. A first carrier sampler can query `classify_uv` on the CPU to select intended face samples, while retaining classification cost explicitly. Producing positions on a rectangle is not yet tessellating a trimmed face.

### C++: sufficient public access for a narrow adapter

`source/SMLib/inc/SmBSplineSurface.h:881–955,1238–1245` provides `GetDegree`, `GetNaturalUVDomain`, `GetKnots` with optional multiplicities, `GetControlPointNet`, `GetControlPoint`, and `SplitAt`. Important concrete semantics:

| API | Returned meaning | Adapter obligation |
| --- | --- | --- |
| `GetControlPointNet` | Euclidean points ordered `u * vCount + v`; empty weights for nonrational geometry | Treat absent weights as one; multiply Euclidean coordinates by rational weights exactly once |
| `GetControlPoint(SM_CP_HOMOGENEOUS_RATIONAL,...)` | Weighted XYZ and W | Preserve homogeneous data; avoid another homogeneous division/multiplication |
| `GetKnots` | Unique knots with optional multiplicities | Do not confuse this with the expanded vector; retain returned domain and endpoint multiplicities |
| `SplitAt(context,t,U/V,left,right)` | New carriers; original unmodified; child domains cover either side of the split | Split copies at existing internal knots, qualify each output and free host owners only after owned data has been copied |
| `CopyAnalyticAsNurb` on a B-spline-derived carrier | Calls the base B-spline copy and returns a plain carrier | Require a supported type; do not silently approximate offset/evaluator surfaces |

The implementation of `GetControlPointNet` confirms Euclidean output and indexing at `source/SMLib/src/SmBSplineSurface.cpp:2789–2844`. `SplitAt:5016–5076` snaps near existing knots and calls the internal split routine; it returns newly allocated `SmBSplineSurface` objects. These are usable public seams without copying upstream extraction code. [Header](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SMLib/inc/SmBSplineSurface.h), [implementation](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SMLib/src/SmBSplineSurface.cpp).

Do not treat the API as a mathematical exactness guarantee. Copy constructors call `sm_FixupKnotVector`; splitting constructs new objects that can run the same fixup. `TrimWithDomain` explicitly warns that interior parameterization can change by more than modeling tolerances and old UV trims should be rebuilt, in `source/SMLib/src/SmBSplineSurfaceNLib.cpp:7405–7455`. It is therefore unsuitable as an assumed identity-preserving original-UV rectangle extractor. A narrow adapter should split on existing span boundaries, preserve **returned** rectangles and check positional/derivative correspondence on its supported family. [Implementation and warning](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SMLib/src/SmBSplineSurfaceNLib.cpp).

`SmCylinder.h:46–70` says the analytic STEP parameter uses degrees and maps nonlinearly to the NURBS parameter, with UV swap/inside-out behavior. `EvaluateSTEP` and ordinary `Evaluate` have different parameter contracts. Preserve NURBS UV provenance for exported patches; converting angle ranges by a constant does not transform the rational parameter or its derivatives. The upstream STEP derivative example is a useful independent illustration. [Cylinder contract](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SMLib/inc/SmCylinder.h), [example](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/Examples/SMLib/step_derivatives.cpp).

### Python export route: available, but not free extraction

`turn_to_nurbs(brep.copy())` followed by `usd.export_brep` is a Python-accessible path to explicit surface arrays in an external USD file. `source/BREP_SM_USD/src/SmuConvert.cpp:1274–1343` writes orders (degree+1), counts, expanded knots, Euclidean vertices and weights; `source/BREP_USD_DATA/src/UsdBrepWrite.cpp:1070–1122` writes the schema attributes. Analytic faces otherwise retain analytic USD representations. [Conversion source](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/BREP_SM_USD/src/SmuConvert.cpp), [schema writer](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/BREP_USD_DATA/src/UsdBrepWrite.cpp).

Limitations are concrete: `turn_to_nurbs` mutates the copied body, removes UV trims, approximates offsets/other curves, and requires reacquiring borrowed geometry. Export can create UV trims/caches and source attributes; use a copy and avoid concurrent access. A full circle can remain multispan, so USD output does not itself produce a single Bézier patch. A first adapter could accept already-single-span NURBS attributes and reject other carriers; owning general knot insertion should be a later deliberate step. USD is an external import boundary here; parse into native records and avoid carrying a USD/object graph into device storage. [Conversion binding](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SmPyLib/src/SmPyBrepOps.cpp), [export contract](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SmPyLib/stubs/usd_brep/usd.pyi).

### Can the first consumer use the sixteen-hole plate?

Yes as a **candidate carrier corpus**, with runtime adapter qualification still required. `benchmarks/cpu/benchmark.py:bored_setup` constructs a box minus straight cylindrical cutters, so planes and cylinders are the expected source family. This supplies rational curved carriers and multiply trimmed planar faces from an actual modeling operation. It does not establish that all final faces meet the first patch contract before inspection.

A minimal C++ experiment adapter can read a saved native body or receive a live host body, enumerate face carriers, copy supported B-spline-derived carriers, split at their existing internal U/V knots and emit only patches satisfying: degrees at most `(3,3)`, exactly degree+1 controls per direction, a clamped single span in each direction, nondegenerate finite returned UV rectangle, and finite strictly positive weights. Unsupported faces are counted and diagnosed. Record parent face ID, immutable snapshot ID and original carrier/returned patch UV rectangles. Keep the face trim description separate; the first GPU kernel changes no topology. Its initial user task can be a dense face-selected sampling/normal job on this plate, compared with a batched owned CPU consumer and reference calls.

This avoids prematurely implementing a general spline extraction engine, at the cost of a C++ experiment-target build/link seam. Header availability, ABI/link setup and runtime output from that adapter remain to be demonstrated. A Python-only route can use USD export, but then must either restrict to already-single-span input or add a deliberate extraction step; it should not pretend those APIs are bound.

## Why a scalar evaluator swap does not accelerate existing Booleans

`SmPyBooleans.cpp` forwards to `SmApiBoolean*`; `SmApiBrep.h:43–104` supplies operands, operation/options and outputs. `SmApiBooleanWithCurves` returns intersection edges from the operation; it does not accept external intersection curves. The inspected public entry points expose no batch-evaluation callback or replacement surface-intersection result protocol. [Python forwarding](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SmPyLib/src/SmPyBooleans.cpp), [public Boolean declarations](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SM_API/inc/SmApiBrep.h).

C++ surface evaluation is virtual, so subclassing is technically possible. That alone is not a supported acceleration hook: the surface must also satisfy geometry type/data, copying, bounds, domain, cache and specialized solver contracts. `SmBSplineSurfaceNLib.cpp:8130–8675` eventually calls CPU `N_SrfDerivs`/power-basis routines and can replace zero tangents with tolerance-sized directions. Point solving combines scalar evaluations, control-net triangle guesses and adaptive local/global retries (`SmSurfacePointSolve.cpp`). A synchronous host call that launches one GPU evaluation would retain that serial control flow and incur launch/synchronization cost per sample. Claims of a transparent Boolean speedup require a source modification plus batching design and measured operation-level results. [Evaluator](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SMLib/src/SmBSplineSurfaceNLib.cpp), [point solver](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SMLib/src/SmSurfacePointSolve.cpp).

Boolean fallback also needs lifecycle planning. The public API modifies the first operand and deletes the second on successful common two-body operations; on failure inputs may remain allocated **but modified**. Retain originals and invoke destructive CPU operations on copies if the owned public operation promises unchanged inputs on failure. Copy/pack/rebuild costs belong in the delivered task time.

## Topology: learn from existing packing, then own identity

SMLib's live edgeuses are pointer-linked mate/radial lists, not a flat manifold halfedge array. `SmEdgeuse.h:39–70` describes alternating mate/radial occurrences; UV trims are attached to an edgeuse/mate pair and may be generated lazily (`:125–136`). `Face.GetEdges` exposes unique objects, whereas ordered edgeuses preserve repeated seam occurrences. [Edgeuse structure](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SMLib/inc/SmEdgeuse.h), [face traversal](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SMLib/inc/SmFace.h).

SMLib already packs topology for exchange in `SmBrepData.h`: face `startLoop/count`, loop `startEU/count`, edge endpoint indices and indexed curve/surface arrays. However records retain pointers back to native objects and optional borrowed geometry; they are not device-transfer structs. `SmuConvert.cpp:1356–1381` adjusts dense indices after removed objects are compacted. Learn the packing boundary while replacing its identity/lifetime model with owned records. [Serial topology](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/SMLib/inc/SmBrepData.h), [compaction mapping](https://github.com/NVIDIA-Omniverse/usd-brep/blob/c9c5979f04cea8c38213004d4f04df0dcfb40d05/source/BREP_SM_USD/src/SmuConvert.cpp).

Truck's live topology uses `Arc<Mutex>` geometry. `truck-base/src/id.rs` explicitly derives `ID` from a raw pointer cast to `usize`; oriented edge/face copies share identity while independently constructed equal geometry does not. `truck-topology/src/compress.rs` maps these identities to dense serialized vertex/edge arrays and oriented boundary references; it describes the compressed form as unsuitable for live editing and validates connectivity/closure when expanding. This clean boundary is useful; raw-pointer identity is unsuitable for an owned persistent/GPU entity ID. [IDs](https://github.com/ricosjp/truck/blob/88ed005249e5e3a6b07f62425399435905cd3ab6/truck-base/src/id.rs), [compressed topology](https://github.com/ricosjp/truck/blob/88ed005249e5e3a6b07f62425399435905cd3ab6/truck-topology/src/compress.rs).

OCCT separates a `TopoDS_TShape` handle, location and orientation. `IsPartner` compares the shared underlying object, `IsSame` also compares location, and `IsEqual` also compares orientation. `TopTools_ShapeMapHasher` deliberately uses `IsSame`, so a shape map does not enumerate all oriented boundary occurrences. `BOPDS_DS` maintains separate operation-local shape indices and same-domain maps. This is a useful contrast between shared entity, occurrence and transient computational index. [Shape semantics](https://github.com/Open-Cascade-SAS/OCCT/blob/b8f597c677811d1f9f4d8a97f5ae2825c0353a42/src/ModelingData/TKBRep/TopoDS/TopoDS_Shape.hxx), [map equality](https://github.com/Open-Cascade-SAS/OCCT/blob/b8f597c677811d1f9f4d8a97f5ae2825c0353a42/src/ModelingData/TKBRep/TopTools/TopTools_ShapeMapHasher.hxx), [Boolean data](https://github.com/Open-Cascade-SAS/OCCT/blob/b8f597c677811d1f9f4d8a97f5ae2825c0353a42/src/ModelingAlgorithms/TKBO/BOPDS/BOPDS_DS.hxx).

OCCT's `BRep_CurveOnClosedSurface` stores two pcurves on the same surface; `BRep_Tool::IsClosed(edge,face)` tests this seam case. `BRep_TEdge` separately carries tolerance, same-parameter, same-range and degenerate flags. Thus an edge→two-distinct-faces assumption fails even for ordinary periodic manifold solids. Preserve coedge occurrences and their UV mappings; never collapse them by `(edgeId, faceId)` alone. [Closed-surface curves](https://github.com/Open-Cascade-SAS/OCCT/blob/b8f597c677811d1f9f4d8a97f5ae2825c0353a42/src/ModelingData/TKBRep/BRep/BRep_CurveOnClosedSurface.hxx), [edge flags](https://github.com/Open-Cascade-SAS/OCCT/blob/b8f597c677811d1f9f4d8a97f5ae2825c0353a42/src/ModelingData/TKBRep/BRep/BRep_TEdge.hxx).

OCCT also exposes lists of `Modified` and `Generated` shapes and an `IsDeleted` predicate through `BOPAlgo_BuilderShape`. A deleted input can still generate other shapes. This confirms that history is a relation with different roles, rather than an old-slot→new-slot permutation or a guarantee of one unique successor. Such history can support naming/UI remapping, but choosing a successor after a split is a separate policy. [Operation history](https://github.com/Open-Cascade-SAS/OCCT/blob/b8f597c677811d1f9f4d8a97f5ae2825c0353a42/src/ModelingAlgorithms/TKBO/BOPAlgo/BOPAlgo_BuilderShape.hxx).

### Proposed owned representation and lifetime contract

This sketch is a design inference for review, not an adopted upstream format.

| Owned native record/array | Contents and identity |
| --- | --- |
| Snapshot | Immutable snapshot ID, body revision, typed array buffers and lifetime owner; launches read exactly one snapshot |
| Entity IDs | Stable typed vertex/edge/face IDs independent of allocation addresses and array slots; host import map assigns them once per snapshot, with persistence/history semantics added deliberately |
| Device slots | Dense indices valid only for one snapshot and one entity table; never returned as persistent user handles |
| Vertex arrays | ID, position, tolerance/flags; incident-edge CSR offsets and slots |
| Edge arrays | ID, endpoint slots, shared 3D curve slot/range, tolerance/flags; incident-coedge CSR including repeated same-face uses |
| Coedge arrays | Occurrence ID, edge slot, loop slot, orientation, UV curve slot/range, edge↔UV correspondence and chart/period offset |
| Loop arrays | ID, face slot, contiguous ordered coedge range, outer/hole/degenerate kind; successor can be derived cyclically within the range |
| Face arrays | ID, carrier slot, UV chart/domain, contiguous loop range, orientation/flags; trim membership remains distinct from rectangular carrier extent |
| Shell/body arrays | Oriented face-use ranges, shell roles and body ownership; face entity identity and occurrence orientation stay separate |
| Patch arrays for iteration one | Parent face ID, snapshot ID, returned carrier UV rectangle, degree pair and homogeneous control range; no topology writes |
| Edit/provenance records | Original→preserved/split/merged/deleted/generated relation, parameter subranges and operation/event identity; one-to-many relations use ranges/CSR |

Keep native pointer lookup maps entirely inside the host adapter while host objects are alive; copy all device-relevant values before releasing them. Even constructing a lazy carrier/cache may change the reference object, so extract from an isolated copy when necessary. The first prototype only promises IDs stable within its immutable import snapshot; long-term history correspondence must not be implied before it is implemented.

Compaction produces new dense slots and explicit old-slot→new-slot and ID→slot mappings for that new snapshot. Retired IDs do not silently identify a newly allocated entity. Outputs are tagged with their source snapshot; stale results cannot apply to an edited body. Keep old snapshot buffers alive until every launch reading them completes. Geometry queries invalidate derived caches by body/snapshot revision rather than native address.

Future edits write separate candidate arrays, not live native graphs. Parallel count/scan/fill and event grouping can build contiguous adjacency, then validate incidence, loop closure, orientation and 3D/UV agreement before publishing a new body snapshot. A failed operation leaves the old snapshot authoritative. Intersection-event identities include source face/edge identities, branch provenance and isolating parameter regions; tolerance-coordinate welding alone can merge nearby distinct branches and is not an identity rule. An edit-history map records splits and merges without claiming that every design-level name has a unique successor.

## What the other implementations actually contribute

Truck's `transversal/integrate/mod.rs` triangulates each shell, builds intersection loop stores, divides faces, classifies unknown components using mesh crossings and fits intersection curves. `intersection_curve/mod.rs:151–176` explicitly gets interference from polygon meshes before constructing refined curved intersection objects. Its traits isolate evaluation, parameter division and inverse search, making ownership boundaries legible. Those synchronous traits are not already GPU batch interfaces, and mesh-seeded discovery is not an independent completeness mechanism. [Boolean progression](https://github.com/ricosjp/truck/blob/88ed005249e5e3a6b07f62425399435905cd3ab6/truck-shapeops/src/transversal/integrate/mod.rs), [intersection seeding](https://github.com/ricosjp/truck/blob/88ed005249e5e3a6b07f62425399435905cd3ab6/truck-shapeops/src/transversal/intersection_curve/mod.rs).

Warp's native BVH separates packed bounds/child indices from query state and supports device construction/refitting with parallel reductions and child counters. This is a scheduling/layout reference. Its mesh and BVH geometry use `vec3 = vec_t<3,float>`; existing mesh closest-point/ray/sign queries concern triangles, not trimmed rational carriers. Bounds narrowed to float need conservative outward rounding/inflation or an owned FP64 path before they can safely exclude CAD intersections. Current default wheels in the inspected README require Turing or newer and CUDA 13.4; CUDA 12 wheels/source builds are separate. No P100 adoption/support claim follows from the generic GPU API. [BVH](https://github.com/NVIDIA/warp/blob/28159649a2bb8b91e1badf692007c38a9f62d6b5/warp/native/bvh.h), [mesh queries](https://github.com/NVIDIA/warp/blob/28159649a2bb8b91e1badf692007c38a9f62d6b5/warp/native/mesh.h), [precision alias](https://github.com/NVIDIA/warp/blob/28159649a2bb8b91e1badf692007c38a9f62d6b5/warp/native/vec.h), [deployment README](https://github.com/NVIDIA/warp/blob/28159649a2bb8b91e1badf692007c38a9f62d6b5/README.md).

Geogram's `mesh_surface_intersection.cpp:276–402` separates candidate-box filtering from parallel triangle intersection; later work constructs exact events, radial bundles and classified arrangements. `find_or_create_exact_vertex:820–837` keys a map by exact homogeneous coordinates and writes approximate doubles to the mesh while retaining exact construction data. This differs materially from epsilon welding. The current implementation still uses host maps/spinlocks and CPU `parallel_for`; translating those containers literally to CUDA would miss the owned event/scan/grouping opportunity. Its exactness applies to supplied mesh geometry, not to the completeness of a curved approximation. [Arrangement implementation](https://github.com/BrunoLevy/geogram/blob/390b14d5b9df949c45d07d5af208700f6be3a616/src/lib/geogram/mesh/mesh_surface_intersection.cpp).

OCCT's Bézier converter copies a B-spline, segments it, increases internal knot multiplicities to degree and selects degree+1 poles/weights per patch. It also returns the original knot boundaries for mapping normalized Bézier coordinates back to the carrier. This is a useful source model for later owned extraction, not a selected library. `BOPAlgo_PaveFiller` then illustrates how much a complete Boolean pipeline includes: VV/VE/EE/VF/EF, repeat intersections after vertex enlargement, FF, blocks and pcurves. FF acceleration alone leaves the rest of the operation. [Conversion](https://github.com/Open-Cascade-SAS/OCCT/blob/b8f597c677811d1f9f4d8a97f5ae2825c0353a42/src/ModelingData/TKGeomBase/GeomConvert/GeomConvert_BSplineSurfaceToBezierSurface.cxx), [intersection phases](https://github.com/Open-Cascade-SAS/OCCT/blob/b8f597c677811d1f9f4d8a97f5ae2825c0353a42/src/ModelingAlgorithms/TKBO/BOPAlgo/BOPAlgo_PaveFiller.cxx).

## Progress judged by delivered modeling value

Each stage inherits the geometry/identity/failure contract of earlier stages. Evaluation throughput is a diagnostic, not a deliverable by itself.

| Stage | First user-value task | Added machinery and completion evidence | Cost/failure that remains visible |
| --- | --- | --- | --- |
| 1: batched carrier evaluation | Dense positions/normals/derivatives on supported real model carriers, e.g. a sixteen-hole plate | Qualified public-API adapter; native immutable patches; analytical/owned-CPU comparisons; a query result with parent face/UV provenance | Copy/extraction, face classification, upload, launch, download and validation; unsupported carrier counts |
| 2: inverse queries | Batched surface projection/distance for inspection or fitting | GPU bounds plus multi-seed/local refinement and boundary candidates; distinction between candidate/local solution and globally resolved distance | Failed refinement, trim/seam/pole handling, ambiguous/global CPU fallback; do not label a Newton root globally nearest |
| 3: bounded tessellation | Export a useful CAD display/analysis mesh at a requested geometric error | Patch refinement, trim arrangement/clipping, shared-edge boundary sampling, ordered mesh output and direct chord/topology checks | Trim holes, periodic seams, curve/surface mismatch and fallback; rectangle tessellation alone does not complete this stage |
| 4: conservative broad phase | Assembly interference screening or pruning before owned intersection jobs | Owned conservative patch/face bounds and candidate pairs; no supported intersection is culled | False positives, CPU refinement and packing cost; it cannot prune inside unmodified SMLib Booleans through the inspected API |
| 5: regular SSI | Reliable section curves between supported transverse surfaces | Complete supported branch graph plus corresponding 3D/two-UV boundaries; original trims and period offsets retained | Closed-loop discovery, tangency, overlap and singular boxes remain explicit unresolved cases or operation fallback |
| 6: narrow curved Boolean | A supported plate/cutter or analytic/low-degree solid operation returning editable curved topology | Face arrangements, cell classification, shared identities, oriented shell output and transactional publication | Original-preserving CPU-copy fallback, classification ambiguity and unimplemented contact families; benchmark entire modeling task |
| 7: GPU topology | Many-pair or repeated owned Booleans without CPU graph assembly becoming dominant | Device scan/group/arrangement/classification; immutable compaction mappings; edit provenance | Exceptional arithmetic/SSI work and memory exhaustion; “GPU” placement does not weaken completeness |
| 8: features and broader kernel | Supported sweeps, offsets and fillets used in an actual modeling sequence | Explicit feature semantics, trim-aware joins and difficult-family SSI/arrangement coverage | Offsets/rolling-ball fillets add their own singularity and self-intersection problems; existing Boolean coverage does not certify them |

Stages 2–4 can change order after operation-level profiles identify the first useful consumer. Batched distance or mesh export is a more honest selective-acceleration deliverable than promising that evaluation automatically reduces the measured hole-cutting time. For every stage report cold versus reused snapshot costs, total operation time, resolved/unsupported/fallback work and output validity. A fallback percentage by pair count alone hides expensive difficult pairs; record time and geometric family too.

## Remaining design decisions

The first iteration should own only supported patch evaluation and immutable provenance. It needs a demonstrated source-input adapter and one concrete consumer; it should not mutate topology, rebuild imported trims or present carrier rectangles as valid trimmed faces.

Before regular SSI and Boolean ownership, resolve the supported surface family, tolerance/separation assumptions, same/coincident/tangent semantics, all-branch completion conditions, curve-to-UV correspondence, and unresolved-work protocol. The [earlier topology study](2026-10-13-gpu-topology.md) describes the primary literature and known completeness limits. A GPU-led kernel can initially use whole-operation CPU fallback, but a full-device claim eventually requires either device support for its declared difficult families or an explicit narrower support scope. Do not hide these semantics in a generic “robustness” checkbox.
